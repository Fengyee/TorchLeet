# ML 系统设计：面试入门指南

适用于 Applied MLE、Research Scientist（RS）和 Research Engineer（RE）面试，重点是计算机视觉、多模态和生成模型。

**先记住一件事：**面试不是背架构，而是把需求问清楚，提出一个能工作的方案，用数据和数字解释取舍。下面的数字只用于练习估算，不是硬件承诺；回答时要说明自己的假设。

## 1. 45 分钟怎么安排

不用逐项回答所有问题。先画出端到端流程，再根据面试官的兴趣深入。

| 时间 | 讨论内容 | 最终要说清楚 |
|---|---|---|
| 0–5 分钟 | 用户、目标、规模、延迟、预算、隐私 | 成功是什么；哪些限制最重要 |
| 5–10 分钟 | ML 问题与数据 | 输入输出、标签来源、简单基线、数据风险 |
| 10–20 分钟 | 模型与评估 | 为什么选这个模型；离线指标怎样对应产品目标 |
| 20–32 分钟 | 服务架构与估算 | 画流程图；估算 QPS、延迟、存储或 GPU 数 |
| 32–40 分钟 | 上线、监控与故障 | 如何灰度发布、发现问题、回滚或降级 |
| 40–45 分钟 | 风险与取舍 | 隐私、公平性、安全；总结选择和后续改进 |

如果是研究岗位，少讲产品服务，多讲研究假设、基线、评估和消融实验。如果是 RE 岗位，多讲吞吐、显存、通信、故障恢复和成本。

### 开场先问这五件事

1. 谁在使用系统？系统要帮助用户完成什么？
2. 规模多大？例如每天请求数、数据总量和增长速度。
3. 要多快、要多新？区分在线（毫秒至秒）、近线（秒至分钟）和离线（小时至天）。
4. 错误的代价是什么？误报和漏报哪个更糟？
5. 有什么限制？预算、设备、隐私、数据授权或地区要求。

信息不全时，先声明假设再继续；不要花十分钟盘问所有细节。

## 2. 通用设计步骤

### 第一步：定义目标和指标

把三件事连起来说：

**训练目标 → 离线指标 → 产品指标**

例如，图像检索可以是：对比学习损失 → Recall@10（相关结果是否出现在前十名）→ 每次搜索的购买率。离线分数变好不一定让产品变好，所以最终要用线上实验验证。

同时说明简单基线：规则、现成预训练模型或小模型。先有基线，才能判断复杂模型是否值得。

### 第二步：说明数据从哪里来

- 标签来自人工标注、用户反馈、业务记录，还是已有数据集？
- 用户点击等隐式反馈便宜，但会受到展示位置和旧模型影响。
- 按用户、商品、场景或时间切分数据；相似图片不要同时进入训练集和测试集。
- 检查类别不平衡、重复数据、授权、个人信息和训练/测试数据泄漏。
- 先做一小批人工复核，了解标签质量再扩大训练。

### 第三步：从简单模型逐步增加复杂度

先用启发式规则或预训练模型建立端到端基线，再根据错误分析决定是否微调、更换模型或增加重排阶段。

常见检索流程：

```text
输入 → 预处理 → 向量编码 → 快速召回候选 → 精细重排 → 业务规则 → 返回结果
```

“召回”优先找全，“重排”再仔细排序。昂贵模型只处理少量候选，通常比对所有请求都运行大模型更省。

### 第四步：选对评估方法

| 任务 | 常见离线指标 |
|---|---|
| 分类 | 类别不平衡时看 PR-AUC、指定精确率下的召回率；也检查校准 |
| 检测 / 分割 | mAP、mIoU；按类别、尺寸和场景分组看错误 |
| 检索 / 排序 | Recall@k、NDCG@k；近似检索的召回率要和精确检索分开评估 |
| 图像生成 | 人工比较、图文一致性和多样性；不要只看 FID |
| 服务 | 端到端 p50/p99 延迟、吞吐、错误率、每次请求成本 |

线上实验提前选定一个主要指标和少数护栏指标。护栏可包括延迟、错误率、安全事件、成本或整体业务指标。

### 第五步：设计服务并考虑失败

画出在线请求路径，也画出离线数据更新路径。明确哪些内容可以提前计算（例如商品向量），哪些必须实时计算。

- 给每个阶段分配延迟预算，预算总和不超过目标；最后用真实端到端数据验证。
- 大模型可用批处理、缓存、量化或蒸馏降低成本；缓存要考虑隐私和过期数据。
- 新模型先影子运行，再小流量灰度；保留回滚方案。
- 模型或依赖不可用时，明确降级策略，例如旧模型、热门结果或人工审核。
- 监控延迟、错误率、队列长度、模型输入分布、分组质量和成本。

## 3. 估算公式：先写单位，再代数字

这些公式用 GitHub 支持的独立公式格式显示。符号和假设要在面试中说明。

### 请求量与并发

$$
\text{平均 QPS} = \frac{\text{每天请求数}}{86{,}400}
$$

每天 100 万次请求约为 12 次/秒。若高峰是平均值的 3 倍，设计时按约 36 次/秒估算。

$$
\text{并发请求数} \approx \text{QPS} \times \text{平均延迟（秒）}
$$

例如 100 QPS、平均延迟 0.2 秒，约有 20 个请求同时处理中。这里用平均延迟估并发，不代表 p99 延迟。

### 存储与 GPU

$$
\text{存储量} = \text{项目数} \times \text{每项字节数} \times \text{保留时间}
$$

$$
\text{所需 GPU 数} \approx
\frac{\text{高峰 QPS} \times \text{每请求 GPU 秒数}}
{\text{目标利用率}}
$$

GPU 估算还要考虑冗余、批处理效率、模型加载和高峰波动。利用率不能假设为 100%。

### 训练模型的显存与计算量

使用混合精度 AdamW 训练时，可先用 **每个参数约 16 字节**估算权重、梯度和优化器状态；这不包含激活值、临时缓冲和框架开销。具体实现可能不同，最终要实测峰值显存。

对稠密 Transformer，训练计算量可粗略估为：

$$
\text{训练 FLOPs} \approx 6 \times N \times D
$$

其中 `N` 是参数量，`D` 是训练 token 数。它是粗略估算，不含所有注意力开销、重计算和多模态编码器成本。

$$
\text{训练时间（秒）} \approx
\frac{\text{训练 FLOPs}}
{\text{GPU 数} \times \text{单卡峰值 FLOP/s} \times \text{实际利用率}}
$$

实际利用率会受通信、数据读取、序列长度和实现影响。先用小规模试跑测吞吐，再更新估算。

## 4. 四个常见设计例子

### A. 以图搜商品

**目标：**用户上传照片，找到相似且有库存的商品。

```text
图片 → 检测商品区域 → 编码成向量 → 向量索引召回 → 重排 → 检查库存并返回
```

- 基线：预训练图像编码器加精确近邻搜索；先在小商品集上验证效果。
- 主要难点：商品图是干净棚拍，用户照片可能有遮挡、背景和光线变化。
- 数据切分按商品 ID，避免同一商品的图片同时进入训练和测试。
- 指标：相关商品 Recall@k、人工相关性、搜索后的点击/购买；分开测向量模型和近似索引质量。
- 取舍：索引压缩可省内存但可能降低召回；更大的重排模型可能提高质量但增加延迟。
- 更新：新商品进入临时索引；库存状态实时过滤；换编码器时要同步重建索引。

### B. 图片内容审核

**目标：**尽快处理高风险内容，同时减少误伤。

```text
上传 → 便宜规则/小模型筛查 → 高风险内容交大模型或人工复核 → 处置并记录申诉
```

- 分级处理：简单、明确的内容自动处理；不确定内容进入人工审核。
- 分类别设定阈值，因为漏掉严重内容和误删正常内容的代价不同。
- 评估要看各类别的精确率、召回率、人工队列积压和申诉改判率。
- 监控新型规避方式、不同语言/群体的错误率和审核员负担。
- 明确保存期限、访问权限和升级申诉流程。

### C. 文生图服务

**目标：**用户提交提示词，系统安全地生成图片。

```text
请求 → 提示词安全检查 → 排队/调度 → 生成模型 → 输出安全检查 → 返回图片
```

- 先定清楚分辨率、每次生成张数、目标等待时间和拒绝内容范围。
- 生成是计算密集型任务；根据每张图的实测 GPU 秒数估成本和容量。
- 队列要有配额、超时和取消能力；可用较少采样步数或较低分辨率降级。
- 输入和输出都要做安全检查；记录最少必要信息，并提供举报机制。
- 评估使用人工偏好、提示词遵循度、安全性和多样性，不以单一自动分数作为结论。

### D. 多模态模型训练平台（RE）

**目标：**稳定地训练一个图文模型，并能在故障后恢复。

- 数据：记录数据、标签和过滤规则的版本；检查重复、授权和评测集污染。
- 资源：估算模型状态、激活值、训练 FLOPs 和数据读取速度；用小规模训练验证吞吐。
- 并行：模型能放进单卡时可用数据并行；状态放不下时考虑 FSDP/ZeRO；超大模型再考虑张量或流水线并行。
- 可靠性：定期保存可恢复检查点，监控每步耗时、显存、梯度和数据加载；故障后从已验证检查点继续。
- 评估：验证集和安全评测异步运行，不要让评测意外阻塞训练。

## 5. 常见术语（够用版）

| 术语 | 简单解释 |
|---|---|
| QPS | 每秒请求数 |
| p50 / p99 | 一半 / 99% 请求不超过的延迟 |
| 召回（retrieval recall） | 相关结果有没有被候选检索阶段找出来 |
| 重排（re-ranking） | 对少量候选用更精细的方法重新排序 |
| 灰度发布（canary） | 先给少量用户使用新版本，观察后再扩大 |
| 数据漂移 | 线上数据与训练数据的分布发生变化 |
| 训练-服务偏差 | 训练和线上预处理不一致，导致输入不同 |
| 降级 | 主服务不可用或过载时，切换到更简单的可用方案 |
| FSDP / ZeRO | 把模型训练状态分摊到多张 GPU 上 |
| MFU | 实际模型计算吞吐占 GPU 理论峰值的比例 |
